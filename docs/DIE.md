# The CPU die: floorplans, links and levels of detail

Code: `src/render/die/cpuplan.ts` (the data model), `src/render/die/cpufloor.ts` (the slicing layout and the channel router), `src/render/die/diepulse.ts` (pulses, packets, trails and cell texts, shared with the GPU card), `src/render/die/cpuplans.ts` (the floorplan of each architecture), `src/render/die/cpuplan.test.ts`. Status: **stages 1 and 2 built** (the layout data and its tests; the snapshot data and the die view that draw it in the game, `src/render/die/dieart.ts`, `src/render/die/dieview.ts`, `src/sim/game/pipesnap.ts`). Not built yet: the new CPU parts and their sim features (stage 3). Background: [`CPU.md`](CPU.md) (how the CPU runs, interrupts), [`ENGINES.md`](ENGINES.md) (the pipelines), [`RENDER.md`](RENDER.md) (the board and its buses).

## Why, and what the owner asked for

Every CPU used to share one floorplan (five stage tiles in a row plus filler blocks the sim does not model). Now each architecture has its own die, drawn from what its engine really has. Owner requirements, from the two review rounds:

- every core part visible and linked, laid out like a real processor, for every architecture and every upgrade variant;
- **maximise the use of the die**: the blocks tile it edge to edge (a gutter of 14 between blocks, nothing else);
- the parts that talk to the board sit **on the die edge their package pins are on**;
- **every grid is a full power-of-two rectangle** (never a partial row);
- the wires are **not arrows**: the die is a game component like the board, so wires are trace bundles with pads, and direction is shown by pulses.

## The data model (`cpuplan.ts`)

`cpuPlan(input) -> CpuPlan { arch, cores, die, blocks, links, tiles? }` (in `cpuplans.ts`) in die coordinates (`DIE` from `layout.ts`, 1420 x 1130, centred on the socket). `planInput(engineConfig, extra)` maps a spec's `EngineConfig` plus the feature knobs (`icacheLines`, `ways`, `l2Lines`, `predEntries`, `predBits`, `cores`) to the input, so a new CPU spec renders without drawing code. Plans are cached by input.

- **Block** `{ id, kind, label, sub?, rect, grid?, parent?, stage?, lane?, unit?, zone, core? }`. `grid` = the cells a structure shows, an exact `cols x rows` (`gridExact`: cols * rows = count, so 8 lines are 2 x 4, 16 registers 4 x 4, 64 lines 8 x 8, a prime count one row); datapath units show their 32 bit-slices (`shape [32, 1]`), the memory controller its 6 lanes, PCIe its 21 lanes (12 PCIe, 3 NVMe, 6 DMI, the board's own bus lane counts). `parent` = the stage frame (a pipeline stage's column) the block sits in; `stage` = stage index of a frame (an instruction in that stage lights it); `unit` = the OoO unit (`ALU0 ALU1 MUL LSU`) whose instruction lights the block; `zone` = `edge` (the board-facing ring, shared by cores) or `core`. Block ids are unique per plan; the hover id is per block kind, `cpu.<kind>` (`board.ts` dieHits), so blocks of one kind share a tooltip.
- **Link** `{ id, kind, from, to, pts, lanes, label?, both? }`: an orthogonal polyline from the edge of `from` to the edge of `to` through the gutters, drawn as a bundle of `lanes` (1 to 4) parallel traces with a pad at each end. Kinds: `data`, `mem` (to RAM), `mmio` (device access that skips the cache), `control`, `forward`, `wakeup`, `flush` (mispredict squash), `irq`, `power`.

## The layout engine (`cpufloor.ts`)

`placeTree` and `routeWires` are generic over the block kind: they need only `{id, rect, parent?}` (a block that others name as parent is a container, not an obstacle). `place` and `routeLinks` are the CPU die's instances; the GPU card plan (docs/GPU.md section 7) uses the generic ones.

- **Slicing floorplan**: a tree of `row`/`col` splits and `leaf` blocks with weights (`f`) or fixed sizes (`px`) fills a rectangle exactly (`spans`: whole pixels, the gutter exact). A split with a `frame` draws a stage column behind its children. Because it is a tree, the same floorplan can be laid out in any rectangle (the multicore tiles use this).
- **Channel router** (`routeLinks`): links are given as block pairs only; the router finds the route through the gutters on a 6 px grid (Dijkstra with a distance heuristic, a penalty per bend and for a track another link already uses), keeps 2 px clear of every block (a stage frame is a container, not an obstacle), and ends each route on the facing edges of the two blocks. Neighbours that face each other along enough of their edges (24 or more) are joined by a **jog** (`jog`): out of one block high on its edge, along the gutter, into the other low on its edge, so the trace is long enough to read as a wire and to run a pulse along; blocks that overlap less keep the short straight hop. A link with no route throws, so a floorplan that blocks a wire fails its test.

## The grammar (every architecture)

The die edge is a ring (`EDGE`): **north** the power block (vcore: one stub per VRM phase) and SVID/thermal; **east** the memory controller (the DIMM bus); **south** the clock and PLL (the crystal) and PCIe/NVMe/DMI; **west** USB, the display and the interrupt controller. Bond-pad rows on the die border show where each bus leaves. These are the sides the board's buses use (`render/board.md` "Routing": `mem` east, `nvme`/`dmi`/`pcie`/`clk` south, `usb`/`video` west, `vcore` north). The **system bus** strip under the core joins the caches, the device path and the edge blocks (the memory controller at its east end). The core fills the middle: the pipeline stages in a row, the register file, the I-cache (when there is one) and the D-cache under them, an optional L2 strip above the system bus. Without an I-cache, fetch goes out through the system bus (no invented port).

## The floorplans

| CPU | What is drawn |
|---|---|
| cpu0 unpipelined | A sequencer along the top (five phase cells over the five phase columns); IF (next-PC mux, PC+4, PC, fetch), ID (immediate, decoder), EX (branch, ALU), MEM (device check, load/store), WB; the register file under IF to EX, the D-cache under MEM and WB. No latches, predictor or forwarding. |
| cpu1 five-stage | The same stage columns with the four pipeline registers as thin columns between them; the predictor inside fetch; a hazard unit that stalls until write-back; the redirect/squash wire from the branch unit to fetch. |
| cpu2 forwarding | cpu1 plus the forwarding unit in execute, fed from the EX/MEM and MEM/WB registers. |
| cpu3 two-wide | A pair/issue unit above two decoders, two ALUs, a register file with 4 read and 2 write ports, one load/store unit. |
| cpu4 out of order | Fetch queue (ring), decode (one decoder per lane of width), rename table + dispatch, scheduler, ALU 0, ALU 1, multiplier, load/store, the result bus (wakes the scheduler, fills the ROB, resolves branches), the reorder buffer (ring) committing into the register file under decode. |
| Variants | An I-cache takes the south-west; cache and predictor tables scale their grids; ways are columns; an L2 strip joins both L1s to the system bus; a bigger ROB, scheduler or queue grows its grid; width adds decoders (the frame grows). |
| Multicore (`cores: n`) | n core tiles in the middle (each laid out for its tile's shape, so a tile fills its cell), one shared L2 at their east end, one system bus under them; the edge ring is shared and every tile's PC gets an interrupt line. Server style = many small tiles, HPC style = one big out-of-order tile. The game's multicore CPUs use this plan, live (see "Core tiles"). |

## Inside the blocks (`blockart.ts`)

A block whose job is a piece of logic is drawn as the symbol an engineer would draw, not as a field of identical cells (`GLYPH_KINDS`): the **PC** a row of eight hex digits, **NEXT PC** and **WRITE BACK** a multiplexer with its inputs (`+4`, `br`, `irq`; `alu`, `mem`, `pc+4`), **PC + n** an adder, **FETCH** the words it reads (one strip per lane, each split into the fields of the instruction word: op, rd, rs1, rs2, imm), **IMMEDIATE** the sign copy and the field, the **DECODER** the word and the six control lines it raises (alu, mem, wr, br, imm, sys), the **ALU** the notched trapezoid with operands A and B, an op and a result register, the **MULTIPLIER** a triangle of partial products, **LOAD / STORE** the address adder and the waiting loads and stores. Structures with entries (caches, the register file, the reorder buffer, the predictor, the TLB) keep their cell arrays. A decoder in a narrow column (the two lanes of the 2-wide die) draws the same symbol standing up (`isVertical`). The control parts are symbols too: the **hazard unit** (the destination of the instruction ahead against the sources of the one behind, `=?`, a stall lamp that lights while an instruction waits in decode), the **forwarding unit** (a multiplexer for each operand choosing the register file or a result ahead; it lights for an operand of the executing instruction that is the result of one in memory or write-back), the **pair / issue** logic of the 2-wide die, the **device check** (an address decision: to the cache, or past it to the bus) and the **pipeline latches** (a column of flip-flops).

A GPU card's blocks follow the same rule (`src/render/gpu/gpuglyph.ts`, `GPU_GLYPH_KINDS`, every kind but the SM frame), each a wired schematic with the CPU die's tools: the PCIe block merges its rx/tx lane cells onto a bus into the DMA engine and its credits; the launch registers (`kernel`, `arg0`, `arg1`, `lanes`, `status`) merge onto the bus that raises `go`, with the launch state machine and command queue when there is room; the program counter feeds an adder and a two-input multiplexer (`seq`, `tgt`) that loops back into it, with the target adder (pc + `imm`) and the `&` gate (`bany` and any lane active) under it when the block is tall enough; the fetch is a window of the kernel (`pc`, `+1`, `+2`, the word being fetched lit) and, when wide, a side panel (kernel `base` + `pc` = `addr`, out to `mem`); the decoder fans its fields out (`dst`, `srcA`, `srcB`, `sext`, and `ctl` driving the six control lines over a bus; `decodeGeom`, `fetchGeom`, `pcArea` are the live slots); the scheduler a scoreboard (`v0..v7` per warp, a ready gate per row) into a round robin multiplexer that issues; a warp a card with its state chip, program counter digits, the 16-bit mask and the stack slots; the register file rows of cells with a row decoder on the left and, when tall, the operand latches `A` and `B` under every lane's column (`cellInset` keeps that room out of the cell grid); the lane ALUs the notched trapezoid, and in a roomy cell (`laneUnits`) the operand bus tapping its six units (`add`, `logic`, `shift`, `cmp`, `mul`, `min/max`; `aluUnitOf` maps an op to its unit, which the live layer lights) into the result mux and latch; the mask a bit strip over the stack slots with `push · pop` and `mset cmp` units wired up into the strip; the coalescer lane requests merging onto the lines they touch; the arbiter a column of lane requests onto a bus, a queue per bank, a picker per queue and a `=?` comparator that raises `serialise` (on the two-SM card the queue rows are the bank bars the live layer fills); the banks SRAM with a row decoder, word lines, bit lines and sense amplifiers; a cache an index decoder, the lines (valid bit, tag, data words) and the tag compare (`=?` into `hit`, then a data mux); the card memory rows of words with the memory map, then the row buffer and the controller. The cells the live layer paints over (lanes, warp cards, bank bars, register rows) stay where `gpuCells` and `maskParts` put them.

The card's die is dressed like the CPU package (`gpuFar`, `gpuNear` in `gpuart.ts`): a rim in the tier's accent (cyan the unit, green the warp SM, violet the two-SM card), a ring of bond pads in the margin, a pin-1 mark, and under the blocks a strip with the card's make-up, the colour legend and `PIPELINE CITY · REV A` (`DIE_MARGIN`, 40 units south). Links end in square solder pads, as on the CPU die. Names are written into the symbols: `v0..v7` on the register rows, `pc`, `mask`, `stack` on a warp card, `warp k` on the scoreboard rows, and a memory map on the card memory (kernel code, the two argument words, the frame, from `KERNEL_LAYOUT` and `GPU_FRAME`). The card shares the CPU die's code rather than copying it: `planFar`/`planNear` with a `PlanStyle` in `dieart.ts` draw both (`CPU_STYLE`, `GPU_STYLE`), the pc, fetch and decode symbols are the CPU's `glyph` (`glyphKit`, `aluPoly`, `pcDigits` from `blockart.ts`), and the live layer uses `diepulse.ts` (`packetOn`, `drawPackets`, `drawTrails`, `CellTexts`). Live (`gpuview.ts`): the decoder splits the real instruction word into its slots and lights the control lines (`alu mem wr br imm sys`) it raises, packets run the routed wires of `gpuroute.ts` (front end, registers, lanes, then the coalescer and banks or caches to the card memory; a mask set runs the mask wire backwards) and leave a trail, the block an instruction sits in glows, the card memory reads `vld · N accesses · C cycles`, and the pc and instruction show in the pc, fetch and decode blocks. Every SM sits in a frame with its title (`sm0`, `sm1`; the single SM of gpu1 and gpu2 too, titled `SIMD UNIT` or `SM 0`, its blocks keeping their plain ids). The single unit's front end is a column (PC, fetch, decode), like the CPU's stages.

While the machine runs, `glyphLive` puts the instructions into the symbols (`DieView.glyphs`): the PC's digits are the PC of the instruction being fetched, the fetch block lists the words in it, the decoder shows its word and lights the lines `controlsOf(op)` says it raises, an execution unit shows its operation and operands. 

## Pins (`glyphgeom.ts`)

A link does not stop at the edge of a block that draws a symbol: it runs on into the symbol (`dockLink`, applied after routing) and ends at a **pin**. Outputs leave from the symbol's output pin (the ALU's result register, the multiplier's product, the PC's last digit); inputs enter at its input pin, through a channel just left of the symbol so the trace never crosses it. The ALU, multiplier and load/store take their operands on one input bus that feeds A and B (or base and offset); the **next-PC multiplexer** has three pins (`+4` from PC + n, `br` for the predicted target, the branch redirect and the mispredict squash, `irq` for the interrupt vector, so the INTC link now ends there), write-back has `alu`, `mem` and `pc+4`. `glyphPins(block)` gives the pins in die coordinates, `blockart.ts` draws the symbols with the same numbers, and the plan test requires every link to end on a block edge or on a pin. On a multicore die the links are docked after the tiles are placed, so the pins match the symbols at the tile's size.

## Instructions on the die (`blockart.ts`, `tokentext.ts`, `dieview.ts`)

**There are no boxes on the die.** An instruction is seen in two ways only. Between blocks it is a **pulse** on the die's own wires (`DieView.pulse`, `wirePoint`: always exactly on a trace, passing from one trace into the next at a block edge; with no trace between two blocks there is no pulse, the blocks light): a bright head in its class colour with a halo in a colour of its own (`idColor`, by sequence number) and a short tail, fading in as it leaves a block and out as it arrives. Inside a block it is **what the block shows**: the symbol fills (the PC's digits; the fetch strip with the word; the decoder's strip split into op, rd, rs1, rs2 and imm with the real values, the control lines it raises lighting one after another; the immediate; an execution unit's operation, operands and result; write-back's destination register; the dispatch lanes that leave for the scheduler) and the cell arrays take it (a new fetch-queue, scheduler or reorder-buffer entry grows into its cell with one white flash, carries its address `@c768` and a pip in its colour; the **rename table** maps each register to the newest instruction in flight that will write it, with its address). A block with nothing of its own to fill glows in the instruction's class colour (a stalled one is ringed, a flushed one red). All of it is drawn from far out (wires from zoom 0.25, cells, symbols and pulses from 0.3); only text waits for 0.8.

## Stepping (`Player.seek`, the Trace panel)

While the game is paused the replay does not play (game time is frozen): a window that arrives (a step of the machine) is shown at once at its last cycle, so **+1 cycle** moves the die by one cycle, and the Trace panel's step buttons ask the sim for a snapshot that carries up to 64 cycles (`snapshotAfterStep`, `STEP_TRACE_CYCLES`) so a **+10** or a **+1 tick** keeps its cycles. The player keeps the last 120 windows (`history`); the Trace panel's **scrubber** (back, forward, a slider, the line of the trace you click) sets `scrubCursor` and the die shows the machine at that cycle (`Player.seek`: the window that holds it, the writes before it applied, its beats and writes played). `scrubRange` and `scrubShown` (`src/game/scrub.ts`) tell the panel what the die can show. Running again follows the machine.

**A card steps the same way** (docs/GPU.md): `scrubTarget` (`cpu` or `gpu:<slot>`, `selectScrub`) says what the cursor, range and shown cycle belong to. The `stepGpu` message (`Game.stepGpu`) ticks the paused card for N of its cycles (stops at idle); the snapshot's card `trace` already holds its last 64 instructions, and the card view (`GpuView`) seeks `GpuPlayer` to the cursor (cycles counted from the first instruction of the window, range `0..span`).

## Core tiles (`coreplan.ts`, `diemulti.ts`, `coretiles.ts`)

A multicore CPU's die is the multicore plan (`planOf` passes the spec's `cores`): the core tiles in the middle, the shared L2 and system bus around them. The snapshot carries `cores` (`CoresSnap`, `pipesnap.ts`): one `CoreLive` per logical core (hardware core, parked, job slot, thread number) and one `PipeSnap` per **hardware core** (trace and stored state each; the threads of one core share a pipeline), plus `selected`. `pipe` is the selected core's hardware core's, for the Trace panel (`viewCore` message, `Game.viewCore`, default 0).

`splitPlan` takes the plan apart: the shared part (everything outside the tiles) and, per tile, an ordinary single-core plan (ids without `c<k>.`, positions still on the die, `scale` = tile width / `CORE_TILE_W`). `DieView` (`diemulti.ts`) holds one `PlanView` (`dieview.ts`, the old single-plan view) for the shared part and one per tile, each replaying its own hardware core's cycles, so **every core runs live** and a tile's zoom is the die's zoom times its scale: the insides (names, cells, symbols, packets) appear when you zoom in far enough on that tile. A tile's replay moves on its `motion` plan (`CoreTile.motion`): the tile plus the shared blocks (the shared L2 named `l2` as on a single-core die) and the wires between them, so a miss sends packets out through `dc-l2`, `l2-fab` and `fab-mc` and back, an instruction fetch goes `src-l2`, and an interrupt arrives along `irq` from the controller (the controller and the clock flash too). Art, cells and glyphs stay the tile's own. A single-core die is one `PlanView`.

Zoomed out, each tile wears a **wash** (`drawWash`, faded out between tile zooms 0.3 and 0.6): the tint of the job thread each logical core runs (`threadTint`: hue from the job slot, lightness from the thread, so a job's threads read as a family), its label (`C3 T2`, `idle`, `kernel`) and the pipeline as cells in the instruction-class colours (`pipeCells`; the out-of-order engine shows its four units and the ROB fill); the two threads of a hardware core split the tile. The selected core's tile has an outline, and only its view publishes `scrubRange`/`scrubShown` for the Trace panel's scrubber. `tileModels`/`washModels` (pure) build the models; the Trace panel draws the same models as its core selector.

## Tests (`cpuplan.test.ts`)

For fourteen configurations (every architecture, with and without the optional parts, wide and scalar OoO, 2, 4 and 8 cores): everything inside the die, no overlaps, unique ids, every grid an exact rectangle (power-of-two counts have power-of-two sides), **the blocks cover at least 78% of the die** (55% on a multicore die), the board-facing blocks on the right edge relative to the core, every link's ends on the block edges it names, every segment square and non-zero, **no link through a block it does not connect**, grid counts equal to the configuration, exactly the structures the architecture has, the catalog CPUs plan cleanly, five different floorplans; plus `gridExact`, the slicing layout and the router on small cases.

## The look (built)

A die is drawn like the board's parts, not as a diagram: macro blocks with coloured rim lines and a faint tinted fill; cells as dense arrays; names small in capitals; traces as bundles of thin parallel lines (3.2 apart) ending in solder pads, dashed for the links that carry an event (flush, forward, wakeup, interrupt); bond pads along the die border. The accent of a block is by kind (`KIND_COLOR`: data cyan, memory amber, control magenta, registers green, multiply and reorder violet), of a link by kind (`LINK_COLOR`).

- `cpuArt` (devices.ts, baked with the device, also used by the shop thumbnails) draws the package, the die and `dieFar`: stage frames, blocks, bond pads. That is all the far view shows.
- `DieView` (dieview.ts) draws `dieNear` on top, faded in by zoom: wires from about zoom 0.7, cell arrays from 0.8, the second line of a block from 1.2; names fade by their own size on screen (`label()`); the camera's maximum zoom is 6.
- A **tall, narrow block** (a queue, a latch) carries its name rotated in a 22-wide strip on its left; its cells sit beside it (`isTall`, `cellRects`).

## Live state (built)

Instructions are pulses and filled symbols, not boxes (see "Instructions on the die"); a stalled instruction rings its block, a flush tints it red. The out-of-order **structures** are cells: the reorder buffer (a ring: empty entries are the free space, live entries coloured waiting / executing / done, the head ringed, the tail marked), the scheduler (coloured by why an entry did not issue: operands, memory, unit, head), the fetch queue; each cell shows its mnemonic. **Event flashes** come from the counter changes since the last snapshot: a cache miss lights the D-cache, a retire the register file, an issue the result bus, a flush the fetch stage. **Pulses** run along the data, control and memory links while the machine runs, along the flush link on a flush. A snapshot is a sampled instant, so all of it is state or an event count, never a per-cycle stream.

Hover ids are **one per kind of block** (`cpu.<kind>`, the lanes of a unit share one; the stage frames are not targets); the descriptions are in `src/ui/regions.ts`, and `logic.test.ts` checks that every kind every floorplan writes has one.

Not live yet (the snapshot does not carry them): the interrupt controller's pending lines and the rename table; the ALU's operand and result values (only the operation and its operands as written).

## Motion and what is stored (built)

A snapshot is a sampled instant (100+ CPU cycles apart), so the die plays back a **slow-motion replay** (`diemotion.ts`, 4.5 cycles a second): the snapshot carries the last 24 cycles of every instruction (`TraceSnap`: stage code per cycle, pc, disassembly) and the writes of those cycles (`StoredSnap.events`: register writes, cache hits and fills with the evicted line, predictor updates, loads and stores). The replay rewinds the snapshot's state by those writes to the window's start and applies them cycle by cycle (`StoreReplay`, tested against the engine cycle by cycle), so the register file, the cache lines (address and first word; mnemonic in the I-cache) and the predictor counters show what they hold and change when written. The newest window starts when the current one ends (the old one fades); pausing freezes it.

Instructions are traceable: pulses, packets and the wire left lit behind them (1.5 s) are in the colour of the instruction's class; a fetch sends its address out through the system bus and memory controller and the word comes back through the L2 and I-cache when there are any; a load asks the D-cache, and on a miss the line comes from RAM; a store writes through. A colour key sits under the die.

**Memory** (`ramview.ts`, `ramlayout.ts`, `src/sim/game/ramregions.ts`): the snapshot carries `ram` = a copy of the memory (`image`) and the **regions** that say what lives where (`ramRegionsOf`): the boot ROM (4 KiB, shadowed at address 0), when the OS is up its header, kernel and job table (about 1.9 KiB for OS 1.0: the kernel's 276 words, one header block and the 8-slot job table), and the program the CPU has loaded at `USER_BASE` (named `#07 calc`, its code up to its last return, its data after it). A program **claims memory by using it**: every store sets a dirty flag for its 256-byte page (`Bus.dirty`), and each base tick the pages the running program has written outside the OS and its own image become its `work` regions (`#07 scan data`, its colour, duller); they are released when it ends. The OS memory is the ROM, header, kernel and job table (`protectedPage`); a store there is refused by the memory protection unit and the OS kills the job (docs/OS.md "Memory protection"). The sim's RAM is 64 KiB whatever is installed; the sticks are the physical memory, ascending by slot number (more installed than that shows as free, less spreads the 64 KiB over the chips there are).

Each DRAM chip is a window onto an address range, cut into **pages** of 256 bytes (a block of the drive), and a page is one square cell: the colour is its owner (the ROM grey, the OS pale, a program by its job type, so one kind of program always looks the same), the strength is how full the page is. Cells are redrawn only when the memory changes. Outlines surround each region; a stick is **not aware of how full it is or how many programs run**: it shows only what the OS has put where, a key of colour and name per owner (`ROM 4K`, `OS 1.9K`, `#07 scan 2768`) and a READ / WRITE key. Usage, the process table and per-process memory belong to the OS and are on the CLI monitor (`memoryTable`: `MEM 64K  SYS 5.9K  FREE 58K`, and the running process as `RUN #07 scan  276B+1.5K`, its image plus what it claimed). The page the CPU reads (a fetch or a load: cyan) or writes (a store: magenta) outlines in that colour for 0.7 s, with a READ / WRITE key on each stick (`DieView.onMemory` -> `Live.touchRam`); the bytes themselves are only in the magnifier.

At the CPU die's zoom levels (cells 0.8x, keys 0.85x, details 1.2x; below 0.7x the traces are the picture) a **magnifier** reads the memory around the address touched last (or the program's start): nine words as address, hex and, where it is code (the ROM, the kernel, a program's code), the instruction, else the characters; each instruction has a coloured pill for its class (ALU, load, store, multiply, branch, system; a key under the magnifier), so a code area reads at a glance; the touched word is highlighted in the instruction's colour, a thread joins it to the line it reads, and the footer says what the region is for. It is sized so its text stays readable at any zoom. Not yet: RAM clock ticks as such, and bytes drawn inside a cell (deliberately: the square is the unit).

## Stages

1. **Layout data, router, tests, mock-ups** (built).
2. **Snapshot data and the new renderer** for the five existing CPUs (built: `pipeline.ts`, `BLOCKS`/`STAGES` and the fixed tiles are gone; hover ids and descriptions come from the plan; the thumbnails keep the far die).
3. **Sim features** (I-cache, 2-bit and bigger predictor, set-associative D-cache, shared L2; default off so existing timings do not move), **new CPU parts** and the branching tree, the picker's branching ladder with measured speed numbers.
4. Later: the multicore simulation (`cores > 1`) and the CPU gallery.

## The TLB
A CPU with an MMU (docs/VM.md) has a `tlb` block between the register file and the D-cache: one cell per entry, showing the virtual page and the frame it maps to (state at the snapshot), with links `fetch-tlb` and `lsu-tlb` (translate) and `tlb-walk` to the L2 or the system bus. `PlanInput.tlbEntries` (from `CpuSpec.mmu.tlb`) switches it on; the unpipelined CPU has none.
