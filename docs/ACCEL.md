# Accelerators: GPU, NPU, TPM (design note, T59)

Status: designed; the specs `tpm1`, `gpu1`, `npu1`, `psu3` exist (T68, T69) and do nothing yet. Owner decision 2026-10-24: start on T51. This note covers the GPU (own ISA, fed by the reserved `pcie` power cable), the NPU and the TPM (a header slot on Mainstream and up). It ends with a proposed task split for the owner to approve. Background: [`ARCHITECTURE.md`](ARCHITECTURE.md) "Accelerators" and "Security", unlock rows in [`PROGRESSION.md`](PROGRESSION.md), slots and VRM in [`BOARD.md`](BOARD.md) / [`VRM.md`](VRM.md).

All three follow the existing device rules: a declarative spec in `DEVICE_SPECS`, a typed slot, `idleW` / `loadW` / `heatFactor` / `thermal`, an MMIO range on the bus, programs that reach them through plain loads and stores and poll a status register (no interrupts, no DMA). Numbers below are first guesses for the balance pass.

## Shared shape

- **New device kinds:** `gpu`, `npu`, `tpm`. New slot type `tpm` (a header, one per board on Mainstream and Enthusiast, none on Starter and Basic). GPU and NPU use the existing `pcie` slot, one card per slot, competing with NIC cards (Basic 1, Mainstream 2, Enthusiast 4).
- **New cable:** `pcie` (the PCIe power lead from the PSU, already reserved in `cables.ts`). Same rules as `cpu`: needs a PSU that has the connector, `pruneCables` unplugs it when the source goes. A card whose spec says `needsPcieCable` and has it unplugged fails POST with `short: "GPU power cable"` (the card is detected but cannot start), not `noPower`.
- **PSU connector:** `psu0` / `psu1` have no PCIe lead, `psu2` (250 W ATX+) has one, `psu3` (500 W, planned) two, `psu4` (1 kW) four. A spec field `pcieLeads` on the PSU; `connectCable("pcie")` refuses with "this PSU has no PCIe power lead".
- **Clock domains:** each card gets its own domain named after its slot (`pcie0`, `pcie1`), like drives. TPM runs on a fixed slow domain `tpm` (no overclock).
- **Bus and MMIO:** each device takes a fixed window in the device range (command / status / data registers plus, for GPU and NPU, a small on-card memory window). The CPU writes a command descriptor, sets `go`, polls `status`. The crossing has explicit latency (PCIe hop: about 8 CPU-domain ticks each way; TPM header: about 20, it is slow on purpose). Bus traffic shows on the board as today.
- **Fast model:** how accelerators key the calibration cache waits for the fast-model design note (T54, T87).
- **Save:** devices go in `board.devices` as today; `Cables` gains `pcie`, filled `false` for older saves with no version bump (additive, see SAVE.md).
- **Sandbox:** every tier offered, as for every other kind.

## GPU

- **ISA:** its own small instruction set on the same assembler framework (second opcode table, same R/I/S/B formats, 32-bit words). Lane registers (8 vector registers of N lanes), a lane id register, an execution mask, vector ALU ops, `vld` / `vst` to on-card memory, a mask-set compare, `bar` (lockstep barrier, trivial in v1) and `halt`. Opcodes are the implementer's choice (ARCHITECTURE "Open questions").
- **ISA as built (T74, `src/sim/isa/gpu.ts`, assembler `src/sim/asm/gpu.ts`, `assembleGpu`):** 8 vector registers `v0..v7` (one 32-bit value per lane), the execution mask, a mask stack (8 deep) and word memory on the card. Only active lanes run an instruction. Formats reuse the CPU's field positions (op in bits 6:0, rd 10:7, rs1 14:11, rs2 18:15, 17-bit immediates).
  - Vector ALU: `vadd vsub vand vor vxor vsll vsrl vsra vslt vmul vmin vmax` (`vd, vs1, vs2`), `vaddi vandi vslli vsrli vsrai` (`vd, vs, imm`), `vli vd, imm` (splat), `lane vd` (lane id), pseudo `vmv vd, vs`.
  - Memory: `vld vd, imm(vs)` gathers and `vst vs2, imm(vs1)` scatters, per active lane, byte address = lane's register + imm, word aligned.
  - Mask: `mseteq msetne msetlt msetge vs1, vs2` set `mask &= (vs1 cmp vs2)` per lane; `mpush`, `melse` (mask = saved mask minus the current one), `mpop` (restore) make an `if / else`; `bany off` branches while any lane is active (a loop runs until its last lane is done), `jmp off` is uniform; both offsets are byte offsets from the instruction (labels in the assembler).
  - `bar` (lockstep barrier, a no-op with one unit) and `halt`.
- **Reference interpreter and kernels as built (T75, `src/sim/ref/gpuref.ts`, `src/sim/gen/gpukernels.ts`):** `GpuRef` runs a kernel functionally with the engine's timing rule written down once: every instruction is 1 cycle, a `vld`/`vst` takes `bankCycles` = the most distinct addresses any one bank (`word % banks`) has to serve (lanes on the same address share one access, masked-off lanes take no part). It counts `cycles`, `conflictCycles` and `idleLaneSlots` (divergence), faults on a bad access, a mask stack error or an illegal word, and `run(max)` throws when a kernel never halts. The kernels are in `src/sim/gen/gpupicture.ts` (see "Picture jobs"); `KERNEL_LAYOUT` puts the code at 0, the two parameter words (`phase`, `level`) at 0x700 and the 64 x 40 picture at 0x800 (`GPU_FRAME`); `gpuKernelExpected` is the plain-JS result a launch is checked against.
- **Device as built (T76, `src/sim/machine/gpu.ts`, `GpuPort`):** one 64K bus window per PCIe slot at `GPU_BASE + k x GPU_STRIDE` (`GPU_PORTS` = `pcie0..pcie3`, constants in `memmap.ts`), clock domain named after the slot, attached by the game (`syncGpus`) when a working GPU sits in the slot and gone when it burns or leaves. Registers (word access): `STATUS` (Busy 1, Error 2, Present 4, Done 8), `CMD` (write 1 to launch, fires on the low byte), `KERNEL` (byte address), `LANES` (0 = all), then read-only `LANES_MAX`, `MEM_BYTES`, `BANKS`, `CYCLES` (last kernel) and `FAULT` (1 bad launch, 2 kernel fault). Card memory is the window at `GPU_MEM` (0x1000): the CPU copies code and data in with plain stores, launches, polls, copies the result out. A launch starts `GPU_HOP_TICKS` (8) card ticks after CMD, the kernel then runs one card cycle per tick (on `gpu1` one instruction, its conflicted `vld` / `vst` taking the extra accesses; the warp engines issue per cycle, GPU.md section 5), and Done shows 8 ticks after it halts; so a launch costs 16 ticks of overhead plus the kernel's cycles, which is why a tiny job is not worth sending. The hop is counted in the card's own clock (ACCEL.md first said CPU ticks; the card has no view of the CPU clock). Card memory is volatile (cleared at power-on), a launch while busy, with too many lanes or a bad kernel address sets Error, and a kernel fault ends the launch with Error and `FAULT` = 2. The card steps the reference interpreter's core, so it matches it by construction; the tests check results, tick counts and a golden trace (blur3 in `gpu.test.ts`, 8 lanes, 1 bank: 462 instructions, 602 cycles, 140 lost to conflicts, 618 ticks; an older figure of 93/205/221 here was out of date). Thermal load is 1 while a launch is in flight and 0 otherwise.
- **Tiers as built (T80, T135):** `gpu2` and `gpu3` are their own engines, not more lanes: the unit (`gpu1`), a two-warp SM with a scoreboard, coalescing and global latency (`gpu2`), and two such SMs with L1s and a shared L2 (`gpu3`); see the table below and [`GPU.md`](GPU.md) section 4. Also `npu2` (8x8, 5 / 45 W, cable, $10,000), `tpm2` (measure 1, attest 20, surcharge 1, $1,500) and `psu4` (1 kW, 4 leads, $2,400). Every tier beats the one below on blur3 (`gpu.test.ts` "GPU tiers"). Card heat is sized so a card at full load settles near 70 C (throttle at 80).
- **TPM and the `secure` job as built (T72, T73; `src/sim/machine/tpm.ts`, template `secure.sign`):** one 4K window at `TPM_BASE`, registers `STATUS` (Busy, Error, Present, Done, Protected), `CMD`, `ARG0`, `ARG1`, `RESULT`, `FAULT`; commands Measure (word hash of a RAM range, `measureTicks` per word), Attest (machine PRNG word xor the nonce, the only PRNG use), Seal / Unseal (a handle to a value, 10 ticks, kept in the module across power cycles, lost if the module is pulled), Protect / Unprotect. Every command crosses the header in 20 module ticks each way. Protected mode is a guard on the bus that applies only while the CPU is executing (`Bus.guardOn`, set by the machine around the engine's step, so the game's own peeks at RAM are never refused): a RAM access inside the range costs `surcharge` extra CPU cycles (the machine stalls the CPU), outside it a read gives 0, a write is dropped, and the game crashes and reboots the machine with "protected-mode violation", like a thermal error. The module runs on one fixed clock (the `tpm` domain) while installed. The reference interpreter has an instant fake TPM at the same address (`RefMemory`), so `runReference` runs the job. `secure.sign` measures its data, attests the measurement, hashes the data in protected mode (range = from its own start to the scratch buffer), seals and unseals the digest and prints its low 6 bits. Class `secure` (level 9) needs a TPM and, like the other classes with unmet needs, arrives and sits unrunnable until one is installed (the "refused, not queued" wording of the first design was not built: the existing arrival rule is the same for every class).
- **NPU and the `npu` job as built (T78, T79; `src/sim/machine/npu.ts`, `src/sim/gen/npukernels.ts`, template `npu.infer`):** one 64K window per PCIe slot at `NPU_BASE + k x NPU_STRIDE`, port and clock domain `npuK` for the card in slot `pcieK`, the GPU's registers and status bits (`DESC`, `COUNT` instead of `KERNEL`, `LANES`). The descriptors (4 words: op, a, b, c) are `Load` / `Matmul` / `Macc` / `Bias` / `Relu` / `Store` on K x K tiles in 4 tile registers and an accumulator, as designed, with the costs `1 + K` (load, store, bias), `2 + 3K` (a product: setup, fill, rows, drain) and 2 (relu), plus one macro-op, `Layer`, added because the CPU has to copy every descriptor into card memory with plain stores (no DMA) and a hundred tile descriptors cost more than the card saves: `Layer` takes a 6-word block `[W, X, OUT, bias, n, relu]` and does a whole dense layer, charging what the tile walk would (`T x T x (T x (2 + 3K) + 2 + K)`, T = n / K). npu1 is clocked like the GPU (base 2, so it can overclock and throttle), npu2 base 3. A card is stepped one descriptor at a time with the PCIe hop each way, like the GPU. The `npu.infer` job is a network of `min(6, 1 + scale)` dense layers, `X <- relu(W X + b)`, on an 8 x 8 batch with seeded small weights; it prints the sum of the final activations. The fallback chain is by what the machine has: an NPU (copy the data and one `Layer` per layer, launch once), else a GPU (a layer kernel, one launch per layer), else a CPU loop. The same line and the same pay on every path; the tests (`npujob.test.ts`, `npu.game.test.ts`) check strictly more ticks down the chain (npu2, npu1, gpu1, cpu) on a bare machine and in a Game.
- **Art as built (T81, T82):** `src/render/board/accelart.ts` draws the cards and the module (see render/case.md): a GPU shows one, two or three fans by tier on a shroud (edge-on modules like the case fans), the bracket with display ports and a plug block (two on `gpu3`); an NPU shows its 4x4 or 8x8 grid of cells (a heatsink and a lead block on `npu2`); the TPM module stands on the board's existing `TPM` header (Mainstream and Enthusiast), with a shield on `tpm2`. They are hit-tested and hovered like the NIC. Shop, shelf and picker tiles use the same drawings (`thumbs.ts`; a graphics card shows its die under the fans), the picker compares (GPU) SMs, warps, lanes, L2, clock, card memory and power, (NPU) matrix cells, (TPM) measure / attest / overhead, every stat has a plain-words tooltip, an installed card whose PCIe lead is unplugged says so in red, and an empty PCIe slot says it also takes cards. **The GPU's insides** (floorplan per tier, block symbols, the card player, hover ids, stepping) are in [`GPU.md`](GPU.md) section 7 and [`DIE.md`](DIE.md). Not built yet: the NPU's MAC grid with its descriptor list (it needs `NpuPort` to expose its tiles, current descriptor and phase the way `GpuPort.view()` and `TpmPort.view()` do), and hover ids for it. The TPM is built, see "TPM internal view".
- **Model:** lockstep lanes under a mask, in three engines (`simd`, `warp`, `multi`): designed and built as in [`GPU.md`](GPU.md). Divergence is real: both sides of a branch run under the mask, the idle lanes are drawn dark. On-card memory is small and banked; bank conflicts serialize, so memory-bound kernels look memory-bound.
- **Launch:** the CPU copies inputs into the card window with stores (no DMA, so the copy cost is visible), writes the descriptor (kernel address, lane count, args), sets `go`, polls. Kernel code lives in card memory and is loaded the same way.
- **Tiers** (prices are orders of magnitude only):

| id | shape | card memory | clock base | W idle / load | PCIe cable | price | level |
|---|---|---|---|---|---|---|---|
| `gpu1` | 1 SM x 1 warp x 8 | 16K | 2 | 4 / 40 | yes | about $1,500 | 10 |
| `gpu2` | 1 SM x 2 warps x 16 lanes | 32K, 2 banks | 3 | 8 / 90 | yes | about $5,000 | 14 |
| `gpu3` | 2 SMs x 2 warps (32 lanes), L1 + shared L2 | 64K, 4 banks | 4 | 12 / 180 | yes, 2 leads | about $15,000 | 16 |

- **Thermal:** its own cooler, built into the card (`passive` high, no cooler slot), throttles like a CPU. Fans on the card are art, not a part.
- **Display:** `display1` (level 10, a part like `display0`, same slot) is the graphics display. Its OS screen is a dashboard (clock, temperature, power, disk, memory bar, IPC trace, process table; `room/screenmodel.ts`, `screenview.ts`); the OS's boot text still shows as on `display0`. Its video cable can go to the board's HDMI port or to a display port on a GPU's bracket (`Game.video` = `"board"` or the slot, `connectCable("video", "pcie1")`, saved as `video`; refused on a text monitor, without a working card in that slot, or while powered; it comes out when the card or the graphics display leaves). With the cable on a card the screen shows the dashboard as usual and the card's frame (its output array as a grid, a status strip) appears as a panel under the process table while a `gpu` job draws and for 8 ticks after (every `gpu` job draws the same 16:10 picture, 64 x 40 words, 10 KB, on every card, as a few frames of an animation: the display plays them as the launches finish (docs/render/live.md); see "Picture jobs" below) (docs/render/live.md "Screen modes"). Without the link the job still runs and pays, it just shows nothing.

## NPU

- **Not a second programmable ISA** (scope). The NPU is a fixed-function systolic matmul / activation unit driven by **command descriptors**: `load tile`, `matmul`, `add bias`, `relu`, `store tile`. The CPU builds a short descriptor list in card memory and launches it. This keeps the emulation cost small while still giving a visible structure (a K x K grid of MACs where data flows right and down).
- **Model:** cost per descriptor = tile setup + `K` ticks fill + one tick per row + drain. Bigger grids finish matmuls faster but cost the same setup, so small jobs gain less (a real trade-off against the GPU, which can also run `npu` jobs, see below).
- **Tiers:**

| id | grid | card memory | W idle / load | PCIe cable | price | level |
|---|---|---|---|---|---|---|
| `npu1` | 4 x 4 | 8K | 2 / 15 | no (slot power only) | about $2,500 | 12 |
| `npu2` | 8 x 8 | 32K | 5 / 45 | yes | about $10,000 | 16 |

- `npu1` needs no cable on purpose: an efficient card a player can add to a Mainstream PSU budget.

## TPM

- **Slot:** the `tpm` header (owner decision 12 in PROGRESSION.md: not a PCIe card, so PCIe stays free for NICs and GPUs). A small daughterboard on the header, no cable, no clock control.
- **MMIO commands:** `measure` (hash a range of RAM, cost per word read through the bus, so it is visibly slow), `attest` (fixed latency, returns a quote word), `seal` / `unseal` (key handle). Uses the machine PRNG only for the quote value, so runs stay deterministic.
- **Protected mode:** while a `secure` job runs, RAM traffic outside the job's own range is refused (a fault that kills the job) and every RAM access pays an encryption surcharge (`tpm1` +2 RAM ticks, `tpm2` +1). This is the "real, visible cycle cost" from ARCHITECTURE "Security".
- **Whose accesses are guarded:** the guard belongs to the address space that wrote the `Protect` command (`Bus.guardSpace`: the page table of the core that wrote it, or -1 for physical addresses; `Bus.spaceOf` is set by the machine). An access from any other space is not guarded: the kernel (translation off while it handles an interrupt), other programs and the other cores keep running beside the secure job, and the secure job stays guarded if the OS moves it to another core. Before this the guard hit every core's RAM reads, so on `os4` the kernel's own instruction fetches read 0 while a `secure` job was protected and the sim threw "illegal instruction 0x0" inside the kernel. Test: `tpm.test.ts` "guards only the address space that asked for it". The range is virtual (the view and the crash report show it so): in a paged space `Protect` resolves it page by page through the writing core's table (`Bus.translate`, `Mmu.peek`) into a set of physical frames, the guard tests the frame (page granular) and on a miss re-resolves once, so a page mapped after `Protect` is accepted; `Measure` reads through the same table. Translation off, and the instant reference TPM, stay physical. Tests: `tpm.test.ts` "in a paged space", `tpm.game.test.ts` "protected mode under the paged OS". Only `secure.verify` and `secure.measure` print something derived from `Measure`; `secure.sign` feeds it to `Attest` and shows neither (its printed digest comes from the checksum kernel).
- **Tiers:**

| id | measure cost | attest latency | encryption surcharge | W | price | level |
|---|---|---|---|---|---|---|
| `tpm1` | 4 ticks / word | 60 | +2 | 0.2 / 0.5 | about $400 | 9 |
| `tpm2` | 1 tick / word | 20 | +1 | 0.3 / 0.8 | about $1,500 | 13 |

- The header exists from Mainstream (level 5) but stays empty until level 9: the empty header is drawn on the board as a hint.

## Job classes

All three classes already exist in `levels.ts` as never-running classes (T50); this makes them runnable. Each is a generator template ([`GEN.md`](GEN.md)) emitting real CPU code plus device code:

- **Built (T77):** template `gpu.render` (docs/GEN.md), class `gpu` (level 10, `needs: []`, `payMul` 3), kernels in `src/sim/gen/gpukernels.ts` with their CPU twins. Every kernel now draws a picture (below); Tests (`gpujob.test.ts`, `gpu.game.test.ts`): the card path prints the same line as the CPU path and takes fewer ticks for every kernel; a Game serves the job with and without a card.
- **Picture jobs (`gpupicture.ts`):** all GPU jobs draw a 64 x 40 picture (2,560 words, 10 KB: the 16K `gpu1` holds it), `framesOf(scale)` frames of it (2 at scale 1, else 4), one launch per frame; the program writes the frame's `phase` (how far the scene has moved) and `level` (the job's own number) to the two words at 0x700 (the CPU twins read them from RAM at `CPU_PARAM`, 0x7000) and launches. The scene is a small integer shader (three moving triangle waves, a plasma, 0..192) made from the element number, so no input array is copied: `vadd` is a brightness change (level -60..60, clamped), `saxpy` contrast (gain level/8 around mid-grey), `thresh` a threshold mask (a computer-vision step; an if and an else under the lane mask), `blur3` a box blur level steps wide (three scene reads), `poly` a tone curve (a blend toward the square). `mandel` colours the escape count (<< 4) with an iteration budget growing over the frames, `sphere` is eight lit checkered balls in two rows whose checker spins (period 16). The display shows words as 0..255 brightness. The seed alone decides the printed checksum (sum of the last picture, `& 63`), never the card; the CPU twin is 0.2 to 1.3 million instructions per job, which is what the card saves.
- **`gpu`** ("render frame" / "batch shader"): with a working GPU (and its cable) the CPU kernel copies a seeded input tile to card memory, uploads a GPU kernel, launches, polls, reads back a checksum and prints it on the CLI. Without one, the generator emits an equivalent CPU loop that prints the same checksum, only slower. GPU kernels: `vadd`, `saxpy`, `blur3` (divergent at the edges), `mandel` (heavy divergence). Same pay either way.
- **`npu`** ("inference"): with an NPU the CPU builds a 2 to 6 descriptor list (seeded layer sizes), launches, polls, prints the class index. The fallback chain is NPU, then GPU (a slower kernel), then CPU (a slower loop). All three print the same class index and pay the same; the speed gap down the chain is what the card sells, so the NPU is an upgrade, not a key.
- **`secure`** ("signed transaction"): `measure` the job's code range, `attest`, run a small hash / checksum kernel in protected mode, `seal` the result, print the quote. The only class that needs its hardware: accepted only with a TPM. Pays more per tick than `db` to make up for the surcharge.

Only `secure` is gated: its arrival is refused (not queued) without a TPM, with the reason on the hover ("needs a TPM"). `gpu` and `npu` jobs are never refused for lack of a card. The job mix weights per level are already in PROGRESSION.md.

## Board and VRM demand

- **The board VRM feeds the CPU only.** GPU and NPU cards have their own VRM on the card (part of the card spec, folded into its `heatFactor`), and draw from the PSU through the slot (up to 75 W) plus the `pcie` cable. So they add **PSU watts and case heat**, not board-VRM amps. This keeps VRM.md's model unchanged and keeps the board choice about the CPU.
- **Slot power cap:** a card with `loadW > 75` must have `needsPcieCable` (all GPUs; `npu2`). The PSU rule counts the card's `loadW` in the rated load as today.
- **Case heat:** card heat raises the ambient for other parts by a small amount (`ambientRiseC = 0.05 x card W`), so a 180 W `gpu3` warms the CPU by about 9 degrees without case fans (`fan1`, planned level 7, offsets it). This is the one new thermal coupling.
- **TPM:** under 1 W, ignored by the VRM, counted in the PSU sum.
- **Built (T71):** `ThermalModel` draws a GPU through the clocked path (its clock scales its watts and its throttle, like a CPU) and an NPU or TPM at `idleW + (loadW - idleW) x load` like a NIC. The accelerator load defaults to 0 (idle) until a device drives it. `CASE_HEAT_C_PER_W` (0.05) times the watts of the working cards is `th.caseRiseC`, added to the ambient of every non-card part and of both VRMs; cards do not warm themselves. Tests: `vrm.test.ts` "cards in the case".

## TPM internal view (as built)

The module is drawn like the CPU die and the GPU card: a tiled floorplan (`render/tpm/tpmplans.ts`, the layout engine and router of `die/cpufloor.ts`), `planFar` / `planNear` of `die/dieart.ts` with the module's colours (`tpm/tpmart.ts`), a symbol in each block (`tpm/tpmglyph.ts`, the CPU die's `glyphKit`), pulses on the routed wires, a hover id per block. Seen from afar it is a lid over a small daughterboard (`accelart.ts` `tpmCover`, a padlock on it shut while protected mode is on); zoomed in (lid fades 1.0 to 1.8, names from 2.2, second lines from 3.4 on a camera that goes to 6) the lid fades out and the die shows through. The die is 1500 x 480 units scaled to about 0.23 into the band under the lid (`board/tpmlayout.ts`), so it wants zoom 3 and more to read.

| Block (`tpm0.<id>`) | What it shows |
|---|---|
| `lpc` | the header lanes (clk, frame, ad0 to ad3, rst) with bits marching in or out while a command crosses, the hop meter |
| `regs` | the six registers as hex digits, the status flags as chips (ERR and PRT in red), the row being written or read lit |
| `seq` | the four states (idle, in, work, out), the bar of the phase's ticks, the command and its fault by name |
| `hash` | word in, the round unit (4 steps on `tpm1`, one on `tpm2`, from `measureTicks`), the accumulator with the running hash, seed, words done |
| `quote` | nonce xor the shift register, the signing rounds (3 on `tpm1`, 1 on `tpm2`, from `attestTicks`), the quote |
| `vault` | eight slots, handle and value, the one a seal or unseal touches lit |
| `ramport` | address and data latches, req / ack, the RAM bus lanes (a measure reads RAM through it) |
| `guard` | a ruler over RAM with the protected window on it, lo / hi, the two comparators and the gate, ALLOW and TRAP, the surcharge, the padlock |

Data: `Snapshot.tpm` is `TpmPort.view()` (phase, registers, protected range, sealed values, running hash, the last 8 commands). A command takes a few dozen module ticks, far less than a frame, so `tpm/tpmplayer.ts` replays each command that finished since the last look in slow motion (about 1.2 s plus the work), from the log entry: it knows the command, arguments, answer and work time, never the words of a hash, so a replay shows the count of words but not the running hash. A command in flight in the module itself is shown live. The route a command takes is `tpm/tpmroute.ts`. Tests: `tpm/tpmplan.test.ts` (tiling, every wire routes, the tiers differ), `tpmroute.test.ts`, `tpmplayer.test.ts`, `board/tpmlayout.test.ts`, `ui/panels/tpmdesc.test.ts` (every id has a description), `sim/machine/tpm.test.ts` "the module's view". The old plan of a lock badge on the RAM sticks is dropped (owner): protected mode shows on the module only.

## NPU internal view (as built)

Built like the TPM's: a tiled floorplan of the die (`render/npu/npuplans.ts`, the layout engine and router of `die/cpufloor.ts`), `planFar` / `planNear` of `die/dieart.ts` in the card's colours (`npu/npuart.ts`), a symbol in each block (`npu/npuglyph.ts`, the CPU die's `glyphKit`), pulses on the routed wires, a hover id per part. Seen from afar the card is a lid over its die (`accelart.ts` `npuCover`: fins, the array's grid etched in it; a metal frame on `npu2`); zoomed in (lid fades 0.4 to 0.7, names from 0.75, second lines and the sums in the cells from 1.5) the die shows through. The die grows with the array in length only (`npuDie`: 1240 x 500 for 4 x 4, 1640 x 500 for 8 x 8) and the card with it (`board/npulayout.ts`: 1500 and 1900 board units long, the die 160 units in from the bracket). **One slot envelope for every accelerator card:** a GPU and an NPU are both `CARD_H` (600) tall and hang `CARD_TOP` (150) above their slot's rail (`board/gpulayout.ts`, used by `accelart.ts` `cardRect` / `cardOrigin`), so cards in neighbouring slots (700 apart) never overlap and a mixed stack lines up; only the length differs by tier. A new card kind must use these two numbers (`accelart.test.ts` checks every spec).

| Block (`pcie<k>.<id>`) | What it shows |
|---|---|
| `host` | the PCIe lanes (clk, tx0, tx1, rx0, rx1): bits marching in on the transmit lanes while a launch crosses, out on the receive ones for the answer, the hop meter |
| `ctl` | the registers the CPU writes: status chips (BSY ERR DNE PRS), desc, count, cycles, fault, grid; the fault by name |
| `desc` | the first 8 descriptors of the list as the card memory holds them (index, operation, operands), the row being run lit with a bar of its ticks, the finished rows green |
| `tiles` | the four tile registers as K x K cells, lit once loaded, filling row by row during a load, glowing purple when a product reads them |
| `array` | K x K multiply-accumulate cells with the sum each holds. A product sends a wavefront down the diagonals: the cells on it are bright, the activation rows come in from the west and the weight columns from the north, the stubs east and south pulse, the cells behind stay dim, and a cell shows the old sum until the wave has passed it. A layer repeats the sweep once per T x T tile; relu flashes the negative sums, bias lights row by row, a store sweeps the rows out |
| `post` | the bias adder, the max(0, x) unit and the rows of K values in and out |
| `cardmem` | a cell map of card memory like the RAM view (one cell per 16 words, `NPU_CELL_WORDS`; strength = how full, `NpuView.fill`; colour = what the list says lives there: list pink, weights amber, biases violet, results green, data cyan, from `regionsOf`). Outlines: cyan = read, magenta = write, for the card's own accesses (from the logged step) and for the CPU's copies (`NpuView.hostWrites/hostReads/lastWrite/lastRead`, pulses from `Live.touchDevice` through `npuAccess` to `CardView.touch`), with the byte counts under it. The `host-mem` wire from the host block carries those copies in (magenta) and out (cyan) |

Hover ids besides the blocks: `mac<r>x<c>` (each cell), `tile<t>`, `entry<n>` (each row of the queue), `lid`. They carry no GPU kind name (`regs`, `pcie`, `mem` are GPU ids), so `describeId` can route by shape.

Data: `Snapshot.npus` is `NpuPort.view()` per card (`slot` = the PCIe slot): phase, registers, the descriptor on show with the ticks left in it, the first 8 descriptors read out of card memory, the tiles loaded, the accumulator, and the last 16 steps (`NpuStep`: run, index, op, operands, cost, fault, the card-memory byte ranges it read and wrote, the accumulator after it). A launch takes a few dozen card ticks, less than a frame, so `npu/npuplayer.ts` replays each launch that finished since the last look in slow motion (a hop of 0.5 s, a descriptor about 0.4 to 1.7 s by its cost), from the logged steps: it is the picture the card showed, only slower, sums included. A launch in flight in the card itself is shown live and is not replayed after. The wires a descriptor runs are `npu/npuroute.ts` (the fetch from card memory first, then the datapath of its operation). Tests: `npu/npuplan.test.ts` (tiling, every wire routes), `npuroute.test.ts`, `npuplayer.test.ts`, `npuglyph.test.ts` (the live symbols), `board/npulayout.test.ts`, `board/npuview.test.ts`, `ui/panels/npudesc.test.ts` (every id has a description), `sim/machine/npu.test.ts` "the card's view".

### How a job reaches the card

- **Where jobs sit:** an `npu` job is a key in the tray like any other; the bot or player plugs it, the OS ingests it and runs `npuJob` (`sim/gen/templates.ts`). The card's window is memory-mapped at `NPU_BASE + k * NPU_STRIDE` (`k` = the PCIe slot): registers below `NPU_MEM`, card memory from `NPU_MEM` (0x1000).
- **ISA:** none. The card runs 4-word descriptors `(op, a, b, c)`, `NpuOp` Load 1, Matmul 2, Macc 3, Bias 4, Relu 5, Store 6, Layer 7; the generated job only emits `Layer` (one fused layer = tiled matmul, bias, relu, whose parameter block `NpuLayerBlock` sits at `a`).
- **Load (when):** before any register is touched the CPU copies, word by word with ordinary loads and stores (no DMA), the activations (0x0), the weights (0x200), the biases (0x800) and the descriptor list (0x900, `NPU_LAYOUT`) into card memory.
- **Launch:** stores to `DESC`, `COUNT` (layers) and `CMD` = 1, then polls `STATUS` until DNE. The card runs the list in a few dozen card ticks.
- **Read back:** after the last poll the CPU loads the result words one by one from the last layer's buffer (`finalAt`) and sends them to the display.
- **Traces:** each such access reaches `Live.touchRam` -> `touchDevice` -> `deviceAt` (card, `pcie<k>`) -> `slotChain`: a write lights `dmi` then `pcie` toward the card (slot 0 hangs off the CPU's own x16: `pcie` only), a read lights `pcie` then `dmi` coming back. The same access reaches the die view (`npuAccess`, `CardView.touch`). `board/npuflow.test.ts` runs a real job and checks every step above, the counters in `NpuView`, and the lit lanes on all four board tiers.

## Out of scope for this phase

DMA and interrupts, multi-GPU, GPU-to-NPU sharing, a programmable NPU ISA, TPM firmware updates, secure boot of the OS.
