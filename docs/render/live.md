# Rendering: live state (activity, boot, power-off, performance, tracing)

Part of the renderer docs; the hub is [`RENDER.md`](../RENDER.md). Code: `src/render/live.ts`, `src/render/board/ramview.ts`, `src/render/board/gpuview.ts`, `src/render/die/dieview.ts`.

## Files

| File | Role |
|---|---|
| `board/busflow.ts` | the packets on the board's traces (`BusFlow.send`, `slice`), see Activity |
| `board/busmap.ts` | pure: the role of every bus (`BUS_ROLE`) and the chains of hops each message takes (`keyChain`, `driveChain`, `slotChain`, ...), tested per board tier in `busmap.test.ts` |
| `live.ts` | per-snapshot and per-frame state: bus activity, cable glow, PSU readout, monitor text and NO SIGNAL, heat glow, fans, DRAM flashes (a ring round the chip; the memory map itself is `ramview.ts`), boot visuals (PCH glow, USB LED, boot bar), the VRM glow, power-good light, crash flash and the dead-board look. Two roots: `root` (interior) and `ext` (monitor screen, USB / monitor LEDs, video cable glow) |
| `gpuview.ts`, `gpu/gpuplayer.ts` (the card's replay on its own clock: history of windows, `seek`/`resume`, one instruction per SM, a state per warp), `gpulayout.ts` | the graphics cards, alive (`Live` owns the `GpuView`; `Snapshot.gpus` feeds it). `gpulayout.ts` is the pure floorplan (fans along the top edge, then lanes in two rows, vector registers, banks, card memory, mask, mask stack, pc, PCIe link; the art, the hits and the tooltip test all read it). `gpu/gpuplayer.ts` replays the snapshot's last 24 instructions at the die's pace (`GpuPlayer`: a conflicted vld takes its cost in rounds, the newest window replaces the old one when it is over). `gpuview.ts` runs each fan as an edge-on `EdgeFan`, the case fans' look (turns per second from the card's temperature, load and throttle: `fanTurns`), fades the shroud cover out between zoom 0.28 and 0.45 and draws the card's floorplan live, like `PlanView` does for the CPU die (shared `diepulse.ts`): packets and trails along the routes of `gpu/gpuroute.ts`, the glowing block of the instruction on show, the real word in the decode, fetch and pc symbols, the lanes lit by the mask (dark = masked off), the banks with the addresses queued on each (red outline = conflict). Texts from zoom 0.3 (`TEXT_Z`), detail from 0.6. The mask stack shows the card's current depth, not the replayed one |
| `ramview.ts`, `ramlayout.ts` | the memory sticks as a map of RAM (docs/DIE.md "Memory"): one square cell per 256-byte page (colour = owner, strength = fullness; redrawn only when the memory changes), region outlines and a key per stick, the magnifier that reads the touched address as code or data; `ramlayout.ts` is the pure part (chip address ranges, colours, outlines, the lens rows) |

## Activity (what lights up)

Idle is calm: everything is a dim base stroke. A data bus lights only while a message is on it: `board/busflow.ts` (`BusFlow`) runs a **packet** (bright head, the trace glowing behind it, 170-340 game ms per trip, the trace fading 320 ms after it arrives) along the exact lanes, the way the CPU die's packets run. A message goes where the copper goes: `board/busmap.ts` (pure, tested per board tier) names the **chain of hops** each kind of message takes (`keyChain`, `driveChain`, `slotChain`, `boardNetChain`, `BIOS_CHAIN`...), each hop on its own lanes (one SATA port, one M.2, one slot, the USB uplink or one port's pair: `lanesOf` over `Bus.groups`), the next hop starting when the last packet arrives. `Live.fire` sends a chain (at most one per `gap` ms per key); an event fires once; a phase or state that goes on (boot, a busy drive, a card copying, a transfer) is armed by every snapshot (`Live.arm`) and fires every 240 ms for as long as the snapshots say so, so it stops with it. Nothing starts while the machine is quiet (off, tripped, dead, halted, error, cold-boot wait; only POST's pings and the power-on chains are `force`d through the black wait) and a power-off clears the packets on the next frame. The video chain hands its packet on to the HDMI cable outside the case (`extFlow`). `BUS_ROLE` (busmap.ts) gives every bus a role: `data` and `control` carry packets, `power` glows with current, `dark` never moves (a new bus must be classified or the types fail). The messages:

- **Memory bus** (cyan; only the stick that holds the address answers, `touchRam`: every fetch, load and store the die replays; a boot phase streams it) and DRAM chip flashes.
- **Device windows** (`Live.touchDevice`, `busmap.deviceAt`): every device but RAM is memory-mapped and the CPU moves each word itself (no DMA: `machine/storage.ts`, `gpu.ts`), so each load or store the die replays at a device's address is a message on that device's chain, like a RAM access lights its stick. A drive's block is read with loads from its buffer window (drive to CPU) and copied to RAM with stores (the memory bundle lights), a write is the other way; a card's kernel and data go in as stores to its window, one word each, which is the slow part of a launch (the card's `in` / `out` phases are only the 8-tick hop across the link, and stream on top). The key's program window and result words light the key chain, only with a real key in the port.
- **Key (USB stick)**: the hub's 4-lane uplink and the key's port (`KEY_PORT`, usb0) only, never another port, DMI or the chipset: `loading` / `ingesting` read it, `writing` / `flashing` write it. Only with a real key in the port (`snapshot.plugged`): a network job has the same `ingesting` / `flashing` phases (the kernel takes it from a virtual key), and then the ethernet chain below streams instead.
- **SATA drive** (busy, or the OS drive while booting / ingesting / flashing): its cable in the bay, its port's lanes, then DMI (the chipset reaches the CPU over DMI). **M.2**: its own lanes straight to the CPU, no DMI. Reads run toward the CPU, a write (the `ingesting` phase) toward the drive.
- **PCIe card** (`slotChain`): the first slot is the CPU's own x16; the others hang off the chipset, so their messages cross DMI. A GPU in phase `in` is being copied to (host to card), in `out` copied from; while it runs (`run`) the slot is quiet. With the video cable on a card, the picture's packets run only the cable (the board's HDMI lanes stay dark) while the card draws.
- **Ethernet** (`net.transfers`, link up): with the board's jack, jack, PHY, the I/O hub and its uplink to the CPU (`lan`, `phyl`, `usb` uplink); with a NIC, its slot's chain. A download runs toward the CPU, an upload away.
- **POST pings what is installed** (`Live.postProbes`, one every 600 ms in turn while the phase is `posting`, also while the screen is black; each a message out and its reply back): the BIOS (flash over `spi`, then DMI; no reply), the CPU's voltage (`svid`, `pwmc`), the cooler (`fanc` to the CPU_FAN header), every stick of RAM (its bundle), every drive (its chain, as for traffic) and every card on a slot. Only parts that are installed are pinged, so a POST that fails shows what it found (the sim's POST needs the CPU, the cooler, the CPU power and RAM: `bootCheck`).
- **Control**: power-on reads the switch (`hdr`, `lpc`, DMI) and the CPU asks for its voltage (`svid`, then the controller's `pwmc` to the phases), which it asks again when its clock or throttle changes by 1% or more; each POST step sends a code to the top board's debug display (DMI, `dbg`); a new line of text leaves the CPU's `video` lanes. The chipset glows only while one of these (DMI, SATA, SPI, LPC, debug) is on its way.
- **Dark on purpose**: DisplayPort (no display on it), audio, the codec, the RTC, crystals, RGB, the heatsink fans' leads and the 6-pin's rail (nothing in the game moves on them).
- **Power conductors and cables** glow in proportion to current, only while power flows (not off, not tripped): `sqrt(W / budget)` for the conductor's load (CPU watts for the 8-pin and vcore, 55-60% of the total for the 12 V / 24-pin, RAM watts for the 5 V rail). A fully idle machine shows a faint glow.
- **Heat glow** around the CPU / DIMMs only above about 42 C (heat, not load); burnt parts get a dark overlay with a red X.

## Screen modes

`screenMode(osOn, gfx, phase)` (`room/monitor.ts`) picks the glass: `text` (POST/CLI text), `os` (the text status rows of `display0`, and of the graphics display while the OS boots) or `dash` (the graphics display, `display1`, once the OS is up). `setScene` gets `gfx` from the installed display's `visual` (`monitor-gfx`). The dashboard is `ScreenView` (`room/screenview.ts`: one Graphics and pooled Texts at the screen's design size, repainted only when `dashSig` of the `DashModel` changes); `room/screenmodel.ts` `dashModel` is the pure snapshot-to-rows function. `Live.updateDash` keeps what the snapshot lacks: the IPC samples (retired over cycles between snapshots) and the tick each program was first seen running. There is no per-process CPU share in the sim, so the table shows state, memory (image + claimed) and time, and the CPU rows are the machine's.

**GPU frame.** With the graphics display's video cable on a card (`snapshot.videoPort` = `pcie<k>`, `monitorLive`), `Live.updateGpuFrame` works out the card's picture and `updateDash` shows it as a panel under the process table (the table drops to 3 rows, `DashCtx.compact`; the gauges and trace stay): `frameModel` (`screenmodel.ts`) turns the card's output region (`GpuSnap.frame`, the 2560 words at `GPU_FRAME`, empty before the first launch) into a 64 x 40 grid of cells, each word as a brightness over 255 plus a status strip (frame number = launches, DRAWING / DONE / FAULT, cycles, lanes, busy %, conflicts). `FrameView` (`screenview.ts`) paints it, only when it changes. `holdFrame` keeps it up while the card works and `FRAME_HOLD` (8) base ticks after its latest launch (a launch that began and ended between two snapshots still counts, by the launch count), then the panel goes and the table has its rows back. The colours are a heat ramp (`frameColor`); the jobs draw 64 x 40 animations (docs/ACCEL.md "Picture jobs"). The scene is rebuilt when `videoPort` changes (the cable and its route differ). The panel is 690 design units tall.

## Boot visuals

- **PCH** (`chipset`): it gets a violet outline glow and a row of animated activity bars only while a message is on a path through it (`Live.pchUntil`, set by `fire` for chains that use DMI, SATA, SPI, LPC or the debug lanes: POST's pings, a SATA drive, a card in a chipset slot, the power switch). A key load does not touch it.
- **Buses carry the data** (existing lanes only; see Activity): posting reads the BIOS (SPI, DMI); loading runs the key over its port and the hub's uplink to the CPU, and the CPU out to RAM (memory bus); writing runs RAM to the CPU and the CPU out to the key. **No data moves while `halted` or `error`**: those buses and drive activity stay dark, while the fans, the lights and the power conductors keep running.
- **Cold-boot wait**: phase `posting` with `bootProgress` 0 (no POST line yet). The CPU idles, so the monitor is black (no text, no NO SIGNAL when a cable is connected); only POST's pings (BIOS, CPU, cooler, RAM, drives, cards) and the power-on chains light on the buses.
- **USB port LED**: dark with no power, while `halted` or `error`, and with no key. Steady green with a key in (powered, running); blinking amber while loading or writing. A key that the halted machine never read (`keyIgnored`) sits in the port with the LED dark and the key dimmed with a static `NOT READ` label (no blink).
- **Standby look**: a blank screen is not a black slab: while the machine is off (`standbyLook` in `monitor.ts` is `off`) the screen shows dim glass with a faint light in the middle, the chin's skyline mark made large, `PIPELINE CITY` and `STANDBY`, perfectly still (it had a slow breathing glow, a sine of about 9 seconds on the game clock, which read as a bug at low game speed and was removed); during the cold-boot wait (powered, no picture yet: `wait`) the same without the `STANDBY` line. It is not shown with text, the OS screen, NO SIGNAL or without a display. Built in `Live.buildStandby` (design units, under the text), shown by `Live.frameStandby`. The lamp's reflection on the glass and the window's light still fall on it (the light layer).
- **Monitor**: shows `snapshot.display` when `monitorLive`, except during the cold-boot wait (black, the sim has no text yet) and in phase `error` unless `postFailed` (a POST error shows its text; any other error, a PSU trip or a burnt part, shows **NO SIGNAL**). **NO SIGNAL** when a monitor is installed, the machine is **powered** and it is not live (no video cable, burnt monitor) or is in a non-POST error (logic in `monitor.ts`, tested in `monitor.test.ts`); a blank screen when live and the machine is off, and a blank screen with a dark LED when off with no cable. A halted machine shows the sim's text (`NO BOOT MEDIA` / `JOB DONE` lines). After a hard power-off the screen is dark on the next frame. An empty monitor bay is drawn as `MONITOR BAY` (a dashed placeholder, never NO SIGNAL). Its power LED is green when live and powered, amber when live and off. A thin green bar under the picture follows `bootProgress` during `posting` and `loading`.

## Power-off rules (everything that moves needs power)

With the machine off, tripped or dead (`board.burnt`): every fan stops on the next frame (cooler fan or pump, PSU fan and its readout fan, the VRM sink fan), no bus or cable carries pulses or glow, no DRAM flash, drives are still (platter, head, LED), the USB LED is dark, the case lights show only what is true (the green ON light needs power and a working power path; the amber OFF standby light needs a working PSU path, so it is dark when `noPowerReason` is set (no PSU, burnt PSU, ATX unplugged, dead board); ERR is red when the phase is `error`, the PSU tripped or the board is dead), the VRM glow is off and its power-good light is dark (red blinking when dead), the monitor is blank. A powered **halted** machine is the opposite on the fans and lights: fans spin, ON is lit, the case strip is steady amber; only the data paths are quiet. A powered **error** machine (POST failed) has fans spinning, ON lit, ERR red and the strip red. Heat glow stays while parts cool (it is temperature). All animation is on the game clock, so a pause freezes it. The PSU readout snaps to the ambient value (25 C, COLD) on a hard power-off, so there is no cooling tail; while the PSU is on it follows the low-pass of the estimate.

## Performance

Static layers are cached (the tray / power plate chrome is one texture below zoom 0.2, each prop node is cached as a texture below zoom 0.2, the cables are their own small layer): retained geometry, the board texture below zoom 0.2 and the device layer texture (devices, PSU, monitor, cables) below zoom 0.14. Textures are destroyed on rebuild. Per frame JS is the fan rotation, the pooled dot sprites (power cables only), one Graphics redrawn for the packets in flight and one DRAM flash Graphics only while the memory bus is lit. Per snapshot: a few Graphics (heat glow, PSU gauge) and a handful of Text updates (only when the string changed). Measured in headless Chrome with software GL (SwiftShader, 1360x800, GPU-bound and pessimistic), full machine installed: page baseline about 16 ms/frame, overview 19-23 ms (44 ms before the device bake: the device layer alone cost 28 ms), PSU mid-zoom 33 ms, DIMM mid-zoom (zoom 0.35) 62 ms, CPU die 56 ms. Real GPU numbers were not measured. With the assembly props (same setup): bare or assembled overview about 20 ms/frame (mostly 16.7 ms with an occasional 33 ms), dragging a key about 20-33 ms, boot with the PCH and buses lit about 21 ms at overview and about 56 ms at zoom 0.22 (GPU-bound, like the DIMM mid-zoom number above). Before baking the props the overview was 32 ms.

Text sharpness: `Camera.apply` sets every Text's resolution to `textResolutionFor(zoom, devicePixelRatio)` (whole steps, 2 up to 4, so 2 at zoom <= 2 on a 1x display and 3 above it), walking the world tree only when the step changes; `label()` in `ink.ts` starts new text at the current step. Covered by `camera.test.ts`. Frame time was not measured in a browser: below zoom 2 nothing changes (resolution stays 2), above it each step re-rasterises the labels once.

## Following the machine (debugging and detail)
For watching what the CPU and the OS do, and for spotting what looks wrong. Nothing here changes the sim.

- **Events.** The engine's event log (`Ev` in `src/sim/engines/common.ts`) records register writes, cache hits and fills, predictor updates, loads and stores, DRAM row accesses, TLB hits, walks and faults, and now the OS: `Ev.Irq` (an interrupt taken, or a page fault entering the kernel: line, return address, handler), `Ev.Iret` and `Ev.Space` (the page table register written: a new address space, the TLB emptied). The machine reports interrupts and table switches through the optional `Engine.note`. Each snapshot carries the last 24 cycles of events (`pipe.stored.events`).
- **On the die** (`dieview.ts`, replayed cycle by cycle): a TLB entry lights on a hit (cyan) and on a fill after a walk (amber); the interrupt controller lights when an interrupt is taken (magenta) and when `iret` returns (cyan); the TLB block lights on an address-space switch and on a page fault.
- **Trace panel** (Menu > Trace, `src/ui/panels/TracePanel.tsx`, decoding in `src/ui/panels/trace.ts`): the events as lines in words with filters (OS, TLB, Mem, DRAM, Cache, Reg, Pred), a rolling buffer of 500 (overlapping snapshot windows are not repeated), the programs that run with their image and data memory, and the **health** lines (`Snapshot.health`): under the preemptive OS the frame map is checked against the job table (a frame owned by a job that is not running, the timer off while programs run, few free frames), plus the kills and bit flips of the session. A check must fail on several snapshots in a row before it shows, so a line means something is wrong.
- **Stepping.** The panel's buttons pause the game and run the machine one CPU cycle, 10, 100, or one base tick (`step` / `stepTick` messages, `Game.stepCycles`: only the machine runs, in sub-ticks; the economy and thermals wait for the next whole tick). While running, a snapshot sees only its last 24 cycles, so stepping is the way to read every event. A card steps too: with a card selected the panel's buttons send `stepGpu` (`Game.stepGpu`, N card ticks) and the scrubber seeks the card player (`scrubTarget`, docs/GPU.md).

Not built: the page tables as a view in the RAM magnifier (virtual and physical side by side), DRAM refresh and bank-busy time as events, ECC corrections and bit flips as events, a timer block on the die, and a per-program page fault and switch count.
